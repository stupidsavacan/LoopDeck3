# LoopDeck Pack Authoring Contract

Authoring contract revision: 2026-10-04
Target LoopDeck packVersion: 1
Prompt target: modern reasoning models including GPT-5.6 Sol

You are creating a study pack for the current LoopDeck3 application.
Compatibility below means the current pack schema and its learning/PDF semantics.
Do not reproduce old application APIs, backup formats or user-data migration behavior.
This is a strict authoring contract, not a loose style guide.
Produce the final importable pack, not merely an example, when file-generation tools are available.

## 0. Decision order and non-negotiable invariants

Apply these rules in order. A later convenience rule must never override an earlier compatibility or source-fidelity rule.

1. Preserve factual correctness and the supplied material's intended scope.
2. Preserve LoopDeck runtime, worksheet/PDF, import, and ID compatibility.
3. Preserve the intended hierarchy: Folder -> Module -> question `category` -> Question.
4. Preserve source numbering/order where the source provides it.
5. Choose the question type that matches the meaning of the source.
6. Improve study quality with plausible distractors, useful explanations, images, and metadata only when doing so does not violate rules 1-5.
7. Validate the complete result before emitting it.

Do not replace an existing compatible representation with a newer-looking equivalent representation when the change can break downstream behavior. In particular, the English-vocabulary contract in section 3 is compatibility-critical.

## 1. Source authority, verification, and coverage

Treat user-supplied worksheets, PDFs, images, notes, lists, and other study material as the primary factual authority and as the authority for intended test scope.

External verification is allowed and useful when the supplied material is unclear, incomplete, suspicious, or difficult to read:
- use reliable external sources to verify a doubtful transcription, label, spelling, date, value, or interpretation when tools are available;
- use external information to resolve a clearly missing or unreadable fact only when the intended source fact can be established with adequate confidence;
- do not silently replace a supplied fact when an external source disagrees with it;
- when a meaningful conflict remains, preserve the supplied material's role as the study source and report the discrepancy instead of guessing;
- do not expand the tested scope with unrelated outside facts merely because they are correct or useful background knowledge.

Never invent facts to fill coverage. If a source-dependent fact cannot be established, omit that question or clearly report the unresolved ambiguity.

Preserve requested question numbering, vocabulary numbering, ranges, and ordering unless the user explicitly asks for reordering.

## 2. Hierarchy contract: Folder -> Module -> category -> Question

LoopDeck has four authoring levels relevant to study organization:
- Folder: a broad user-recognizable collection such as a school test, term, or explicitly requested grouping.
- Module: one coherent study material, subject range, book range, or user-recognizable study unit.
- question `category`: an internal grouping/filter inside a Module.
- Question: one actual prompt/answer item.

This hierarchy is a hard default. Do not promote source-file boundaries into higher levels.

### Folder rules

- Do not create a Folder merely because the source contains multiple pages, images, chapters, headings, or topics.
- Do not invent subject-taxonomy Folders such as `地理総合` merely to organize a batch unless the user explicitly asked for that Folder or the source already defines that broad collection.
- If the user specifies a test/term/folder, use it.
- If no broad grouping is supplied, prefer one neutral Folder for the imported set rather than inventing several Folders.

### Module rules

- Multiple pages or images from the same coherent material belong to one Module by default.
- Do not create one Module per image, page, worksheet side, heading, or small topic.
- Split into multiple Modules only when the user explicitly requests it or when the supplied sources are clearly independent study materials that should be launched/studied separately.
- A batch of several geography-material images from one study set is therefore normally one geography Module, not several Modules and not several Folders.

### Category rules

Use `category` for useful internal subdivision of one Module.
Choose categories in this priority order:
1. categories explicitly requested by the user;
2. explicit headings, sections, ranges, or groupings in the source;
3. compatibility-preserving groupings required by an existing material format;
4. the minimum additional grouping needed to make a large Module practical.

Do not invent a semantic taxonomy merely because the content can be classified that way. For example, do not reorganize a numbered vocabulary list into inferred categories such as `意見`, `政治`, `感情`, or `行動` unless the user or source explicitly defines those categories.

Several source images may map to several categories when their contents are genuinely different, but image count does not determine category count. Images covering the same topic may share one category.

### Numbered vocabulary category rule

For numbered vocabulary materials such as LEAP:
- preserve the original order and `number` values;
- do not infer semantic categories unless explicitly requested or present in the source;
- when category subdivision is useful and the source gives no categories, use contiguous numeric ranges;
- the default granularity is approximately 25 consecutive vocabulary items per category, for example `001〜025`, `026〜050`, `051〜075`, `076〜100`.

## 3. English vocabulary canonical format and worksheet/PDF compatibility

English vocabulary and phrase-list Modules have a compatibility-critical canonical representation. Keep this representation even if another schema could express the same study behavior.

For a normal numbered English-vocabulary item, use:
- `type: "input"`;
- `prompt`: the English word or phrase itself, with no Japanese question wrapper;
- `answer`: the primary Japanese meaning;
- `acceptableAnswers`: other genuinely correct Japanese meanings that should also appear as worksheet meanings;
- `number`: the original source number;
- `direction: "normal"`;
- no `imageAsset` unless the vocabulary item genuinely depends on an image.

Canonical example:

```json
{
  "id": "school-2026-leap-001",
  "moduleId": "school-2026-leap-001-200",
  "type": "input",
  "number": 1,
  "category": "001〜025",
  "prompt": "agree",
  "answer": "賛成する",
  "acceptableAnswers": ["同意する", "意見が一致する"],
  "direction": "normal"
}
```

Compatibility rules:
- Do not rewrite the prompt as `agree の意味は？`, `「agree」を日本語にすると？`, or another mixed Japanese/English sentence. The worksheet planner detects the compact English prompt.
- Do not set canonical vocabulary items to `direction: "en_to_ja"`; the current Japanese-to-English worksheet/PDF planner intentionally skips those questions.
- Do not convert canonical vocabulary data into a `sides`-only representation. `sides` and `supportedStudyModes` may be added when useful, but they must not replace or alter the canonical `prompt`, `answer`, `acceptableAnswers`, `number`, and `direction` fields.
- Do not move Japanese meaning variants from `acceptableAnswers` into `acceptedAnswers` only. The worksheet/PDF planner reads `answer` plus `acceptableAnswers` when constructing Japanese meaning prompts.
- Normally omit `acceptedAnswers` for canonical vocabulary. If a special judging requirement makes it necessary, keep every worksheet-visible Japanese variant in `acceptableAnswers` as well and make the explicit accepted-answer set complete.
- `choiceCandidates` or `sideChoiceCandidates` may add controlled multiple-choice study without changing the canonical vocabulary representation.

The current worksheet/PDF path turns compact English-prompt/Japanese-answer vocabulary into Japanese-to-English worksheet rows automatically. Preserve that behavior.

## 4. Output target and top-level model

LoopDeck accepts JSON and ZIP imports. Use these canonical LoopDeck filenames:

1. one complete `.loopdeck.json` file containing a LoopDeckPack object; or
2. one `.loopdeck.zip` whose root directly contains:
   - `manifest.json`
   - `modules.json`
   - `questions.json`
   - optional local image files such as `images/map01.png`.

If images are needed, use the ZIP form so the actual local assets can be included.
If no images are needed, a single `.loopdeck.json` is acceptable.
Do not output executable content. LoopDeck study packs are data only.

A complete single-file pack has this shape:

```json
{
  "packVersion": 1,
  "packId": "stable-unique-pack-id",
  "title": "Specific pack title",
  "description": "Optional short description",
  "folders": [
    { "id": "term1-final", "title": "一学期期末" }
  ],
  "modules": [
    {
      "id": "school-2026-term1-final-history-imperialism",
      "folderId": "term1-final",
      "title": "歴史総合 帝国主義とアジア",
      "subject": "歴史総合",
      "description": "Optional module description",
      "tags": ["歴史", "期末"],
      "questionIds": ["school-2026-term1-final-history-imperialism-001"]
    }
  ],
  "questions": []
}
```

For ZIP output:
- `manifest.json` contains packVersion, packId, title, optional description, and folders;
- `modules.json` is the modules array;
- `questions.json` is the questions array.

## 5. Question types

Choose the type by meaning, not by convenience. Do not make every question `input` just because it is easier.

### input

Use when the expected answer is one clear term or short phrase.

```json
{
  "id": "chemistry-ion-001",
  "moduleId": "chemistry-ion",
  "type": "input",
  "number": 1,
  "category": "基本",
  "prompt": "Na+ の名称は？",
  "answer": "ナトリウムイオン",
  "acceptableAnswers": ["Naイオン"],
  "example": "Optional usage example or example sentence",
  "explanation": "Optional post-answer explanation with additional learning value"
}
```

Do not compress multiple independent answers into one input answer.

### choice

Use when exactly one displayed option is correct. For authored high-quality packs, normally provide 4 plausible choices manually.

```json
{
  "id": "history-001",
  "moduleId": "history",
  "type": "choice",
  "number": 1,
  "category": "基本",
  "prompt": "中国同盟会の中心人物は？",
  "choices": ["孫文", "袁世凱", "蒋介石", "康有為"],
  "answer": "孫文",
  "explanation": "Optional concise explanation"
}
```

Rules:
- `answer` must appear in `choices`;
- choices must be unique;
- distractors must be plausible and from the same conceptual class as the answer;
- never use joke or obviously unrelated distractors.

### multi_select

Use when the learner must select the complete applicable set rather than type one short answer. This is appropriate for prompts such as `すべて選べ`, `2つ選べ`, `該当するものを選べ`, or other genuinely multiple-answer tasks.

```json
{
  "id": "history-002",
  "moduleId": "history",
  "type": "multi_select",
  "number": 2,
  "category": "標準",
  "prompt": "三民主義の内容をすべて選べ。",
  "choices": ["民族主義", "民権主義", "民生主義", "帝国主義"],
  "correctChoices": ["民族主義", "民権主義", "民生主義"]
}
```

Every `correctChoices` item must appear in `choices`.
Do not add an `answer` field to `multi_select`.
Do not invent extra correct answers just to force a multi-select question.

## 6. Accepted answers and judging

For input/choice questions:
- `acceptableAnswers` is for true equivalent variants;
- `acceptedAnswers` may be used when an explicit accepted-answer set is needed;
- the primary `answer` is always accepted;
- when a non-empty `acceptedAnswers` array is present, LoopDeck uses it instead of `acceptableAnswers` for judging, so include every intended non-primary accepted variant there;
- do not include vague related concepts, explanations, or partial answers as accepted variants.

Optional `answerJudging` exists for questions that need stricter or structured matching:

```json
{
  "answerJudging": {
    "mode": "any_of",
    "caseSensitive": false,
    "ignoreSpaces": false,
    "ignorePunctuation": false,
    "allowJapaneseSentenceEdges": true
  }
}
```

Supported modes:
- `single`: normal single-answer judging;
- `any_of`: accept any configured accepted answer;
- `all_of`: use `answerJudging.requiredParts`; every required part must occur in the normalized input;
- `exact_phrase`: require an exact normalized accepted answer and do not apply the normal loose sentence-edge matching;
- `numeric`: currently requires an exact normalized accepted answer; it does not provide numeric tolerance/range handling.

Default judging normalizes Unicode with NFKC, trims/compacts surrounding whitespace and edge punctuation, and is case-insensitive unless `caseSensitive` is true. In normal `single` / `any_of` mode, LoopDeck also accepts limited Japanese sentence-edge wrappers and exact English answer tokens inside a longer input. `exact_phrase` disables that loose fallback.

`requiresAll` exists in the TypeScript rule shape but is not consulted by the current judge; do not emit it as an authoring control. Use `mode: "all_of"` with non-empty `requiredParts` instead.

Use custom judging only when the normal answer/accepted-answer behavior is insufficient. Do not assume undocumented tolerance, ordering, numeric ranges, or fuzzy matching behavior.

## 7. Two-sided study and generated-choice study

Input questions may explicitly define both study sides:

```json
{
  "sides": {
    "front": {
      "label": "英語",
      "text": "apple",
      "acceptableAnswers": ["apple"]
    },
    "back": {
      "label": "日本語",
      "text": "りんご",
      "acceptableAnswers": ["リンゴ"]
    }
  },
  "supportedStudyModes": ["front_to_back", "back_to_front"]
}
```

Use this when both directions are pedagogically intended, except that section 3 remains authoritative for canonical English vocabulary storage.
For simple compact Japanese/English vocabulary, LoopDeck can also infer reversible presentation automatically.

Vocabulary-side metadata rules:
- `sides` is additive study metadata. It must not replace compatibility-critical canonical `prompt`, `answer`, `acceptableAnswers`, `number`, or `direction` fields.
- For new English/Japanese vocabulary, add `sides` and `supportedStudyModes` when explicit labels/directions improve study behavior, while keeping section 3's canonical fields unchanged.
- For same-language vocabulary or other pairs whose roles cannot be reliably inferred from script alone, explicit labeled `sides` is strongly required when both directions are intended. Examples include old-Japanese word <-> meaning, kanji <-> reading, term <-> definition, and person <-> achievement.
- Do not force ordinary long-form questions or generic one-question/one-answer material into two-sided cards merely because the schema permits it.

Canonical English vocabulary with additive sides remains shaped like this:

```json
{
  "id": "vocab-001",
  "moduleId": "vocab",
  "type": "input",
  "number": 1,
  "prompt": "pollen",
  "answer": "花粉",
  "acceptableAnswers": ["花粉"],
  "direction": "normal",
  "sides": {
    "front": { "label": "英語", "text": "pollen" },
    "back": { "label": "日本語", "text": "花粉", "acceptableAnswers": ["花粉"] }
  },
  "supportedStudyModes": ["front_to_back", "back_to_front"]
}
```

For same-language vocabulary, labels carry semantic meaning and therefore must be explicit, for example:

```json
{
  "type": "input",
  "prompt": "あはれ",
  "answer": "しみじみと趣深い",
  "sides": {
    "front": { "label": "古語", "text": "あはれ" },
    "back": { "label": "意味", "text": "しみじみと趣深い" }
  },
  "supportedStudyModes": ["front_to_back", "back_to_front"]
}
```

Input questions may use `direction`: `ja_to_en`, `en_to_ja`, or `normal`.
`direction` is consumed by some worksheet/export planning and retained as metadata. Inline reversal comes from explicit `sides` + `supportedStudyModes` or the compact Japanese/English auto-reversal heuristic. Do not rely on `direction` alone for reliable two-direction study.

For controlled distractors when an input question is presented as a choice question, use:

```json
{
  "choiceCandidates": {
    "mode": "manual",
    "choices": ["correct", "distractor A", "distractor B", "distractor C"],
    "distractors": ["distractor A", "distractor B", "distractor C"],
    "reason": "Why these distractors are educationally plausible"
  }
}
```

Runtime rules:
- `choices` is the actual candidate source and must include the primary correct `answer`;
- provide at least 4 unique usable choices for a normal four-choice presentation;
- accepted-answer variants must not be used as distractors;
- `distractors` and `reason` are optional authoring metadata; the current runtime does not use `distractors` as a separate option source.

For explicit two-sided study, `sideChoiceCandidates` may provide different candidate sets for `front_to_back` and `back_to_front` using the same structure and rules.

## 8. Images and image-grounded questions

### Question-specific reference colors and patterns

Use optional `visualReferences` when the source question asks the learner to identify a color or pattern in a map legend, chart, or image. The references appear beside the question/image before answering, in array order. Describe the visual cue without naming the answer. Never invent a source legend or use these swatches as a replacement for the authoritative figure.

```json
"visualReferences": [
  { "type": "color", "color": "#EDB0AA", "label": "上の塗りつぶし：うすい赤の面塗り" },
  { "type": "stripe", "color": "#EF8A84", "backgroundColor": "#FFFFFF", "angle": 90, "spacing": 11, "lineWidth": 4, "label": "下の縦線：赤い縦線模様" },
  { "type": "dots", "color": "#2563EB", "backgroundColor": "#EFF6FF", "spacing": 12, "lineWidth": 4, "shape": "circle", "label": "青い水玉" }
]
```

Each question may have 0–16 references. Each reference requires `type`, a non-empty plain-text `label` (at most 500 characters), and `color` in six-digit `#RRGGBB` form.
- `type`: `color` (solid fill), `stripe` (parallel stripes), `grid` (square grid), `crosshatch` (crossed diagonal lines), `dots` (round dots), or `checker` (checkerboard).
- Optional `shape`: `rectangle` (default) or `circle`, for any type.
- All patterns accept optional `backgroundColor` (six-digit hex, default `#FFFFFF`) and `spacing` (repeat distance in CSS pixels, finite number 4–64, default 12). For `checker`, spacing is the size of one square.
- `stripe`, `grid`, and `crosshatch` accept `angle` (finite number 0–180 degrees): 0 gives horizontal stripes, 90 vertical stripes, 45 diagonal stripes. Defaults: stripe/grid 90, crosshatch 45; grid/crosshatch add a perpendicular second set of lines.
- `stripe`, `grid`, `crosshatch`, and `dots` accept `lineWidth` (finite number 1–32, default 2, strictly less than spacing). For dots, this is the dot diameter.
- `color` accepts no pattern parameters. `dots` and `checker` accept no angle; `checker` accepts no lineWidth. Unknown fields are rejected.
- Only these declarative fields are allowed: never supply CSS expressions, HTML, SVG, URLs, data URLs, scripts, or arbitrary style fields. Labels and prompts remain plain text.
- The metadata survives JSON/ZIP export/import and backups. Swatches need no separate image asset; use ZIP when the question also needs an imageAsset.

Optional image references use `imageAsset`:

```json
{
  "imageAsset": "images/history/map01.png"
}
```

Allowed image extensions:
- .png
- .jpg
- .jpeg
- .webp

Reference/import rules:
- path must be relative and local;
- no remote URLs;
- no absolute paths;
- no `../` traversal;
- no data: or javascript: URLs;
- do not invent image filenames unless you also provide the image file;
- a JSON-only pack cannot carry a local image payload; when any `imageAsset` is required, emit a ZIP that actually contains the referenced files;
- unsafe or unsupported image references are rejected. A safe but missing referenced image produces a warning; the authoring self-check still requires the asset to exist and resolve;
- store one shared figure once and let multiple questions reference the same stable neutral path instead of duplicating the same image per question.

Source authority and fidelity:
- treat a user-supplied worksheet/map/graph/image as factual authority for the figure itself;
- prefer preserving or reusing the supplied source instead of redrawing it;
- cropping, cleanup, or contrast adjustment is allowed only when labels, scale, relationships, and factual meaning are unchanged;
- never invent missing labels, values, legends, locations, or relationships;
- if a required visual fact is unreadable or ambiguous, verify it under section 1 or omit/report it instead of guessing;
- do not generate a factual replacement map/graph/diagram from imagination when the supplied source can be preserved.

Question construction from figures:
- create an image question only when the image materially contributes to answering it;
- each question must target a specific visible feature such as a label, location, line, bar, legend, relationship, sequence, or region;
- one authoritative figure may and should be reused for multiple targeted questions when it contains multiple testable facts;
- keep distractors in the same semantic class as the answer and plausible for that exact figure/context;
- explanations must resolve the visual mapping, not merely repeat that the answer is correct;
- avoid prompts whose answer is already stated verbatim in the prompt.

Asset quality:
- include the actual referenced image files, never placeholders;
- preserve enough resolution/crop/context that labels, text, axes, and legends remain legible at normal phone-scale display;
- do not add decorative or invented factual content;
- do not claim image quality you did not actually create and inspect.

## 9. Safety restrictions

Never put these executable/renderable files in a pack:
- .html / .htm
- .js / .mjs / .cjs
- .css
- .apk / .dex / .jar / .so
- .exe / .bat / .cmd / .sh / .ps1

Do not embed HTML or JavaScript in metadata or question text as a feature. Treat all text fields as plain text.

Current import resource limits:
- whole JSON/ZIP/backup file: at most 32 MiB;
- ZIP entry count: at most 256 entries;
- total ZIP expanded size: at most 64 MiB;
- any one ZIP entry after expansion: at most 12 MiB;
- manifest.json / modules.json / questions.json: at most 8 MiB each;
- each image asset: at most 8 MiB after decoding/expansion.

Keep packs comfortably below these ceilings; they are safety limits, not authoring targets.

## 10. ID, reference, and merge rules

Use stable collision-resistant IDs. IDs are not merely local labels: active packs are resolved by ID, and collisions can change which pack/module/question is visible.

Recommended pattern:
- packId: `school-2026-term1-final`;
- module id: `school-2026-term1-final-history-imperialism`;
- question id: `school-2026-term1-final-history-imperialism-001`.

Requirements:
- packId is non-empty;
- folder IDs are unique;
- module IDs are unique;
- question IDs are unique;
- every module.folderId points to a real folder;
- every question.moduleId points to a real module;
- every module.questionIds entry points to a real question;
- a question listed by a module should belong to that module;
- do not reuse an ID for different content;
- prefer IDs that are unlikely to collide with another imported pack.

Current collision/merge behavior that authors must account for:
- active packs are resolved by `packId`; later entries in the active-pack resolution order win. Imported packs are loaded after the built-in pack, so an imported collision can shadow built-in content;
- module IDs use later-wins precedence, but each module resolves questions only from its owning pack. Question IDs must be globally unique across different active packIds because learning history uses question IDs as keys; direct cross-pack question-ID collisions are rejected;
- importing the same already-imported `packId` offers overwrite or merge update;
- merge update keeps identical colliding questions once; a colliding question with different content is renamed with a suffix such as `__merge_1` and module `questionIds` are remapped;
- during module merge, incoming module metadata replaces same-key metadata while `questionIds` are unioned/de-duplicated;
- a module ID shared with another active pack can trigger module-merge behavior;
- overwrite import replaces the stored assets for that pack with the newly imported referenced assets. Merge import upserts assets: incoming same-path bytes replace stored bytes, while unrelated existing assets remain. Merge preview is pure and does not stage or persist assets;
- use a pack-specific prefix for module/question IDs unless intentional replacement/merge is the goal.

## 11. Module and question metadata

For authored modules, provide non-empty `id`, `folderId`, `title`, `subject`, and a `questionIds` array. Keep module titles specific enough to identify the study material/range, but obey the hierarchy contract in section 2 rather than splitting a Module for every source section.

Only `id` and `questionIds` are required module fields. For clear authored content, provide `folderId`, `title`, and `subject` as well. Missing or malformed optional text metadata is normalized safely: folderId becomes empty, title defaults to id, and subject defaults to その他. A non-empty folderId must reference an existing folder.

Optional module presentation metadata currently consumed by the UI includes:
- `color`
- `accent`
- `accentColor`
- `description`
- `tags`
- `subtitle`
- `preferredAnswerFormat`: `auto`, `choice`, or `input`, used as the module's default answer format.

Folders may also carry `description` and `tags`. Built-in presentation metadata and imported metadata use the same data contract.

`color`, `accent`, and `accentColor` must be six-digit hex colors such as `#2563EB`. Invalid authored values are rejected; omitted colors use inferred/default colors. Removed `sampleMarks` and `sampleColors` fields are not supported authoring features.

Useful optional question metadata currently consumed by the study UI includes:
- `category`: internal category/filter label governed by section 2;
- `number`: numeric range/filter ordering metadata; preserve source numbering;
- `example`: an example sentence, usage example, or concrete example of the studied item;
- `explanation`: post-answer additional learning information such as usage notes, reasoning, etymology, common confusions, grammar notes, or necessary background.

Do not use `explanation` merely to restate the already-encoded `prompt` <-> `answer` relationship, for example `pollen means 花粉`. Do not put an example sentence in `explanation`; use `example` for that. An empty `explanation` is valid when the question/answer relationship is already self-explanatory.

Do not author runtime-derived presentation state such as `activeStudyMode`, `autoReversed`, or `directionLabel`; LoopDeck sets those while presenting a question.
Fields that merely exist in a TypeScript interface but are not wired into the current study UI are not automatically authoring features.

## 12. Importer enforcement versus authoring invariants

The importer validates and normalizes the runtime schema before persistence. It rejects, among other things:
- packVersion other than 1; missing/blank packId or title; missing folders/modules/questions arrays;
- duplicate question IDs and duplicate module IDs within the imported pack;
- missing question id/moduleId/prompt; unsupported question types;
- missing input/choice answer; fewer than 2 choice options; fewer than 2 multi-select options; empty multi-select correctChoices;
- unsafe container paths, unsafe/unsupported image references, forbidden executable/renderable file extensions, and files exceeding the resource limits;
- broken folder/module/question cross-references, inconsistent module ownership, duplicate choice text, choice answers outside choices, and multi-select answers outside choices;
- invalid colors, supported-field types, and preferredAnswerFormat values.

Validation cannot establish factual accuracy, distractor quality, hierarchy intent, worksheet/PDF-compatible vocabulary encoding, or whether a figure really supports an answer. Missing safe image payloads remain warnings rather than fatal errors.

Therefore the mandatory authoring self-check is stricter than the importer. A pack that imports successfully can still behave incorrectly if these invariants are violated.

## 13. Authoring workflow

Before final files, do this internally or visibly when useful:

1. Identify the user's intended Folder and Module structure before writing questions.
2. Apply the hierarchy rules from section 2; do not derive hierarchy from file/page/image count.
3. Detect compatibility-sensitive material such as numbered English vocabulary and lock its canonical representation before adding enhancements.
4. Build a source/coverage plan and preserve source numbering/order.
5. Decide the intended question type for every source fact.
6. Define true accepted-answer variants and plausible distractors.
7. Preserve and inspect required image sources; reuse shared figures.
8. Generate stable IDs and cross-references.
9. Run the mandatory self-check below.
10. Only then emit final JSON/ZIP contents.

## 14. Mandatory self-check

Before presenting the final pack, verify:

- [ ] packVersion is 1.
- [ ] packId and title are non-empty.
- [ ] every folder/module/question ID is unique.
- [ ] every folder has non-empty id/title.
- [ ] every authored module has non-empty id/folderId/title/subject and a questionIds array.
- [ ] every module.folderId exists.
- [ ] every question.moduleId exists.
- [ ] every module.questionIds entry exists and belongs to that module.
- [ ] no Folder or Module was created merely because a source had multiple pages/images/sections/topics.
- [ ] same-material source pages/images remain in one Module unless an explicit rule justified a split.
- [ ] categories follow user/source/range structure and do not introduce an unrequested semantic taxonomy.
- [ ] numbered vocabulary preserves original order/numbers; default invented subdivision, if needed, uses contiguous ~25-item ranges.
